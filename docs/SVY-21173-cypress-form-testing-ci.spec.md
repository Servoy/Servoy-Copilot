# Spec: SVY-21173 — Create a Dedicated Servoy Product for Running Cypress Form Tests Headlessly in CI

## 1. Goal

Create a standalone headless Eclipse/Equinox application (similar to the existing WAR exporter product) that can run on Jenkins without the Servoy Developer IDE UI. This application opens a workspace, starts the embedded Servoy Application Server, discovers all Cypress form tests (`*.spec.cy.js`) across solutions, executes them via headless Cypress, and reports pass/fail results. The target use case is running **form-level Cypress tests** (single-form tests using `formpreview=` URLs) in CI pipelines, *not* full E2E tests against deployed applications.

## 2. Background

### 2.1 Cypress Form Tests vs E2E Tests

The codebase distinguishes two types of Cypress tests:

| Aspect | Form Tests | E2E Tests |
|--------|-----------|-----------|
| Scope | Single form rendered in isolation | Multi-form flows across the application |
| Spec location | `jenkins-custom/e2e-test-scripts/cypress/cy-form/{formName}.spec.cy.js` | `jenkins-custom/e2e-test-scripts/cypress/e2e/{targetForm}.cy.{js,ts}` |
| URL pattern | `http://localhost:{port}/solution/{name}/index.html?formpreview={formName}` | Full application URL (possibly deployed WAR) |
| Runtime needs | Servoy Developer workspace + embedded app server | Deployed application (WAR or dev server) |
| Discovery | `CypressTestDiscoveryService.discoverAllTestForms()` — scans `cy-form/` for `.spec.cy.js` files | `CypressTestDiscoveryService.discoverAllE2ETests()` — scans `e2e/` for `.cy.js/.cy.ts` |
| Generation | Auto-generated from `.frm` files by `FormSpecGenerator.generateSpec()` | Written manually or generated by AI via `ServoyTestingServer.generateCypressE2ETest()` |

**This spec is ONLY about form tests.** E2E tests need a deployed application and do not require the IDE.

### 2.2 How Form Tests Currently Run

In the IDE, form tests are triggered via:
1. **MCP tool** — `ServoyTestingServer.testForm(formName)` calls `FormSpecRunner.runSpec(formName, true)`
2. **Context menu** — `RunCypressFormTestHandler` (single form) and `RunAllCypressFormTestsHandler` (all forms)

The execution flow is:
1. `ensureTestingMode()` → sets `servoy.ngclient.testingMode=true` (enables `data-cy` selectors)
2. `FormSpecGenerator.generateSpec(formName)` → generates `.spec.cy.js` if missing (parses `.frm` file for elements)
3. `FormSpecRunner.runSpec(formName, headless=true)`:
   - Gets workspace root from `ResourcesPlugin.getWorkspace()`
   - Locates spec at `jenkins-custom/e2e-test-scripts/cypress/cy-form/{formName}.spec.cy.js`
   - Ensures `cypress.config.js` exists with `baseUrl = http://localhost:{port}`
   - Ensures Cypress is installed (project-local `node_modules/.bin/cypress` or fallback to bundled)
   - Executes: `cypress run --spec <path> --config-file <config> --config video=true,screenshotOnRunFailure=true`
   - Returns pass/fail output

**Key dependencies** at runtime:
- `ApplicationServerRegistry.get().getWebServerPort()` — needs the embedded Tomcat running
- `ServoyModelManager.getServoyModelManager().getServoyModel().getActiveProject()` — needs Servoy model initialized
- `ResourcesPlugin.getWorkspace().getRoot()` — needs Eclipse workspace
- Node.js + Cypress installed
- No `Display` or SWT UI is required (unlike JSUnit which uses `Display.syncExec`)

### 2.3 How JSUnit Tests Run Outside the IDE

JSUnit tests use `JSUnitLaunchConfigurationDelegate` which creates a launch configuration and launches the Smart Client in test mode. This requires:
- `DLTKTestingPlugin` (DLTK testing framework)
- `Display.syncExec()` for result collection
- Full Eclipse workbench with UI thread

This makes JSUnit tests fundamentally harder to run headlessly. **Cypress form tests are simpler** — they just need an HTTP server serving forms and `ProcessBuilder` to invoke Cypress.

### 2.4 The WAR Exporter as Architecture Precedent

The WAR exporter (`WarWorkspaceExporter`) demonstrates how to run headless Eclipse applications:
- Extends `AbstractWorkspaceExporter<WarArgumentChest>` which implements `IApplication`
- Registered as an Eclipse application via `plugin.xml`
- `start(IApplicationContext)` method:
  1. Calls `ModelUtils.setUIDisabled(true)` — disables UI
  2. Parses command-line arguments into an `IArgumentChest`
  3. Calls `initializeApplicationServer()` which starts the Servoy App Server via `IServerStarter.start(true)`
  4. Calls `ServoyModelFinder.initializeServoyModelProvider("exporter")` — initializes Servoy model
  5. Imports projects into workspace, triggers build
  6. Exports the WAR
  7. Calls `ApplicationServerRegistry.get().doNativeShutdown()`

This is the exact pattern we need — but instead of exporting a WAR at step 6, we discover and run Cypress form tests.

### 2.5 The Pipeline Wizard (`SetupPipelineWizard`)

The pipeline wizard creates the `jenkins-custom/` directory structure with:
- `e2e-test-scripts/cypress/` — Cypress test scripts directory
- Properties files, drivers, plugins for Jenkins
- Configures the Jenkins pipeline job via REST API

The new form test runner must integrate with this existing pipeline infrastructure.

## 3. Design

### 3.1 Headless Eclipse Application: `CypressFormTestRunner`

Create a new Eclipse application (registered in `plugin.xml`) that follows the `AbstractWorkspaceExporter` pattern:

```
com.servoy.eclipse.developer.mcp.headless.CypressFormTestRunner implements IApplication
```

**Lifecycle:**
1. Parse CLI arguments (`--workspace`, `--solution`, `--appServerDir`, `--settingsFile`, `--timeout`, `--outputFormat`, `--specDir`)
2. Initialize application server (reuse `AbstractWorkspaceExporter.initializeApplicationServer()` pattern)
3. Import/open workspace projects
4. Wait for Servoy model to finish loading
5. Set `servoy.ngclient.testingMode=true`
6. Wait for embedded Tomcat to be ready (poll `ApplicationServerRegistry.get().getWebServerPort()`)
7. Discover form tests via `CypressTestDiscoveryService.discoverAllTestForms()`
8. Optionally generate missing specs via `FormSpecGenerator`
9. Execute tests via `FormSpecRunner.runSpec(formName, true)` for each form
10. Aggregate results, output JUnit XML report
11. Shutdown app server and exit with appropriate exit code (0 = all pass, 1 = some fail, 2 = error)

### 3.2 Command-Line Arguments

| Argument | Required | Default | Description |
|----------|----------|---------|-------------|
| `-data <path>` | Yes | — | Eclipse workspace directory (standard Eclipse arg) |
| `-s <name>` | Yes | — | Solution name to activate |
| `-as <path>` | No | Auto-detect | Application server directory |
| `-p <path>` | No | `servoy.properties` | Settings/properties file |
| `-timeout <seconds>` | No | `120` | Per-test timeout |
| `-forms <list>` | No | All discovered | Comma-separated form names to test |
| `-outputDir <path>` | No | `./test-results` | Directory for JUnit XML output |
| `-generateMissing` | No | `false` | Auto-generate specs for forms without them |
| `-port <number>` | No | From `servoy.properties` | Override the embedded Tomcat port (avoids conflicts on multi-executor Jenkins agents) |
| `-cypressArgs <args>` | No | — | Extra args to pass to Cypress |
| `-verbose` | No | `false` | Verbose output |

### 3.3 Test Result Output

The runner produces:
1. **Console output** — summary with pass/fail counts (compatible with Jenkins console parsing)
2. **JUnit XML** — standard `TEST-*.xml` files in `outputDir` for Jenkins JUnit plugin integration
3. **Exit code** — 0 (all pass), 1 (some failed), 2 (infrastructure error)

### 3.4 Reuse of Existing Services

The headless runner reuses these existing services directly:
- `CypressTestDiscoveryService` — discovers test forms
- `FormSpecGenerator` — generates spec files if `--generateMissing`
- `FormSpecRunner` — runs individual specs (already supports headless)
- `RunAllCypressFormTestsHandler.runTestsCore()` — orchestration logic (pass `null` for `IProgressMonitor`)

### 3.5 Application Server Startup in Headless Mode

The embedded Tomcat must start and serve forms via HTTP. This is already handled by `IServerStarter.start(true)` in the exporter pattern. The key difference from WAR export is that we need the web server to remain running while tests execute (WAR export doesn't need it).

Sequence:
1. `IServerStarter.start(true)` — starts app server including Tomcat
2. Poll `ApplicationServerRegistry.get().getWebServerPort()` until > 0
3. Optionally poll `http://localhost:{port}/solution/{name}/index.html` until responsive
4. Run tests
5. `ApplicationServerRegistry.get().doNativeShutdown()`

### 3.6 Eclipse Product Definition

Register the application in the `com.servoy.eclipse.developer.mcp` bundle's `plugin.xml`:

```xml
<extension point="org.eclipse.core.runtime.applications" id="cypressFormTestRunner">
  <application>
    <run class="com.servoy.eclipse.developer.mcp.headless.CypressFormTestRunner"/>
  </application>
</extension>
```

The product can be invoked via:
```bash
./servoy_developer -application com.servoy.eclipse.developer.mcp.cypressFormTestRunner \
  -data /workspace -s mySolution -as /path/to/appserver
```

Or packaged as a dedicated product (`.product` file) for distribution.

### 3.7 Integration with Jenkins Pipeline

The `SetupPipelineWizard` should be extended to optionally include a "Run Form Tests" build step in the generated `Jenkinsfile`. This step would:
1. Check out the workspace
2. Run the headless form test runner
3. Publish JUnit XML results
4. Optionally fail the build on test failures

### 3.8 Alternative: Embed in WAR Exporter

As mentioned in the Jira ticket, an alternative is to add a `--runFormTests` flag to the existing WAR exporter product. This would:
- Run form tests **before** WAR export
- Abort export if tests fail
- Reuse the already-started application server

This is simpler to implement but couples testing with export. The recommended approach is a standalone application that can be composed in pipelines independently.

## 4. Implementation Plan

1. **Create `CypressFormTestArgumentChest`** — CLI argument parser class in `com.servoy.eclipse.developer.mcp.headless` package. Handles `-s`, `-timeout`, `-forms`, `-outputDir`, `-generateMissing`, `-verbose`, `-cypressArgs`.

2. **Create `CypressFormTestRunner`** — main `IApplication` class. Follows `AbstractWorkspaceExporter.start()` pattern:
   - Initialize app server
   - Import workspace projects
   - Wait for Servoy model and Tomcat
   - Delegate to test execution

3. **Create `HeadlessFormTestExecutor`** — orchestrates test discovery and execution:
   - Uses `CypressTestDiscoveryService.discoverAllTestForms()` or explicit form list
   - Calls `FormSpecRunner.runSpec()` for each form
   - Collects results using `RunAllCypressFormTestsHandler.TestRunResult`
   - Handles timeouts and cancellation

4. **Create `JUnitXmlReporter`** — generates standard JUnit XML from test results for Jenkins integration.

5. **Register Eclipse application** — add extension point in `com.servoy.eclipse.developer.mcp/plugin.xml`.

6. **Create product definition** (optional) — `.product` file for standalone distribution similar to the WAR exporter product.

7. **Extend `SetupPipelineWizard`** — add option to include form test step in generated Jenkinsfile. Add a checkbox "Run Cypress form tests before export" on the details page.

8. **Add integration tests** — test the headless runner in `com.servoy.eclipse.developer.mcp.tests` (plugin test that verifies the application can start and discover tests).

9. **Documentation** — update `AGENTS.md` with the new headless runner entry point and usage instructions.

## 5. Acceptance Criteria

- [ ] A headless Eclipse application `com.servoy.eclipse.developer.mcp.cypressFormTestRunner` can be launched from command line
- [ ] The application starts the Servoy Application Server, loads the workspace, and waits for Tomcat to be ready
- [ ] All form tests in `jenkins-custom/e2e-test-scripts/cypress/cy-form/` are discovered and executed
- [ ] Individual form names can be specified via `-forms` argument
- [ ] JUnit XML results are produced in the output directory
- [ ] Exit code 0 when all tests pass, 1 when some fail, 2 on infrastructure error
- [ ] The runner can execute on a Jenkins agent without a display (`-Djava.awt.headless=true`)
- [ ] Existing `FormSpecRunner`, `FormSpecGenerator`, and `CypressTestDiscoveryService` are reused without modification
- [ ] The runner works with the existing `jenkins-custom/` directory structure created by `SetupPipelineWizard`
- [ ] A form test that passes in the IDE also passes when run by the headless runner (same Cypress config, same URLs)

## 6. Out of Scope

- Running E2E tests (those run against a deployed application and don't need the IDE)
- Running JSUnit tests headlessly (requires `Display.syncExec` and DLTK — a separate, larger effort)
- Modifying the form test execution logic in `FormSpecRunner` (it already supports headless)
- Creating a new Cypress test authoring workflow
- Running tests against a deployed WAR (that's E2E, not form testing)
- Automatic Cypress installation on CI agents (assume Node.js + npm are available)

## 7. Resolved Questions

| Question | Decision | Rationale |
|----------|----------|-----------|
| Should the runner be a standalone product or an option on the WAR exporter? | **Standalone product** | Decouples testing from export; can run independently in pipelines; simpler to maintain. |
| Should the embedded Tomcat bind to a random port to avoid conflicts on Jenkins agents? | **Configurable via `-port` CLI arg; default from `servoy.properties`** | No random-port mechanism exists in the Servoy platform (out of scope to add). The headless runner accepts an optional `-port` argument to override the default. It always regenerates `cypress.config.js` with the actual runtime port to avoid stale config. |
| Do we need to support parallel form test execution (multiple Cypress processes)? | **No — sequential execution for v1** | Parallel execution requires multiple Tomcat instances or Cypress's paid parallel service. Form tests are fast individually. Can be revisited as a follow-up if CI times become a problem. |
| Should `--generateMissing` be the default behavior or explicitly opt-in? | **Opt-in (not default)** | In CI, runs should be deterministic — only execute specs committed to source control. Auto-generation is useful in the IDE but not appropriate for CI pipelines. |
| How should database test data setup/teardown work in CI (no live DB on Jenkins)? | **In-memory HSQLDB by default** | The integration tests already use `jdbc:hsqldb:mem:cypress_test`. The runner ships a template `servoy.properties` pointing to HSQLDB. For forms with real data dependencies, users provide their own `servoy.properties` pointing to a CI database. `FormSpecRunner.executeTestSetup()` handles SQL inserts. |
| Should the `SetupPipelineWizard` pipeline step be added now or as a follow-up? | **Follow-up ticket** | The runner is a standalone CLI tool that works independently of the wizard. It only needs `cy-form/` with spec files + Cypress installed. Wizard integration can be added later. |

## 8. Implementation Notes (discovered during headless testing)

### 8.1 Tomcat bundle activation resilience

The `org.apache.tomcat.Activator.start()` iterates all `org.apache.tomcat.serviceprovider` extension-point contributions. If any single provider fails to load (e.g. `com.servoy.eclipse.core.tomcat.ServiceProvider` which depends on a UI workbench), the entire Tomcat bundle fails to activate — preventing the web server from starting.

**Fix applied:** Wrapped each provider/listener registration in a try/catch so that individual failures are logged but don't abort Tomcat startup. This change lives in `org.apache.tomcat/src/org/apache/tomcat/Activator.java`.

### 8.2 `formpreview` auth bypass requires TiNG build

The `formpreview` URL parameter bypasses the solution authenticator via `IndexPageFilter` (in `com.servoy.eclipse.ngclient.ui`). This filter:
1. Looks for `dist/app/browser/index.html` inside `solutionProjectFolder` (set by `Activator.setActiveSolution(name)`)
2. If the file exists → serves it directly, skipping auth entirely
3. If the file does NOT exist → falls through to standard auth flow → shows login page

In the headless runner:
- `com.servoy.eclipse.ngclient.ui.Activator.setActiveSolution()` is never called (normally done by `com.servoy.eclipse.core` during IDE startup)
- The TiNG Angular build may not have run (`-Dservoy.ngclient.titanium.build.disabled=true`)

**Required for tests to pass:**
1. Remove `-Dservoy.ngclient.titanium.build.disabled=true` from VM args (allow the build to generate `dist/app/browser/index.html`)
2. The `CypressFormTestRunner` must call `com.servoy.eclipse.ngclient.ui.Activator.getInstance().setActiveSolution(solutionName)` after solution activation so `IndexPageFilter` can locate the dist folder

### 8.3 Non-critical errors in headless mode

These errors appear during headless startup and are harmless:
- `"Tomcat: failed to load service provider from com.servoy.eclipse.core"` — TomcatTesterServlet not registered (not needed for form tests)
- `"Tomcat: failed to load service provider from com.servoy.eclipse.ui"` — Developer-only servlets (not needed)
- `InjectionException: NoClassDefFoundError: IDeveloperServoyModel` — MCP server servlets can't register (not needed for form testing)
- `"Tomcat: failed to load started listener from com.servoy.eclipse.core"` — TomcatStartedListener not needed in headless mode
