### RULE 4: SERVOY JAVA API LIMITATION - CRITICAL

**⚠️ YOU CANNOT MOCK SERVOY JAVA APIs BY REASSIGNMENT**

In Servoy's JavaScript environment (Rhino), Java objects and methods **CANNOT be reassigned**:

```javascript
// ❌ CANNOT MOCK - Java APIs fail reassignment
application.createWindow = function() { ... }  // Error
databaseManager.getFoundSet = function() { ... }  // Error
plugins.mail.sendMail = function() { ... }  // Error

// ✅ CAN MOCK - JavaScript objects
forms.myForm = { width: 0 };  // OK
globals.myVariable = 123;  // OK
```

**When functions call Java APIs - Two Approaches:**

**OPTION 1 - Integration Tests (RECOMMENDED):**
Test by calling Java APIs directly in real Servoy environment (common in production test suites).

**OPTION 2 - Refactor for Testability:**
Extract business logic into pure functions separate from Java API calls.

**Your Response Pattern:**
```
"I've analyzed [functionName]. It calls Servoy Java APIs:
- application.getActiveWindow()
- databaseManager.getFoundSet()

These cannot be mocked, but I CAN create INTEGRATION TESTS that 
call these APIs directly in the Servoy environment.

Would you like me to:
A) Create integration tests (call APIs directly)
B) Suggest refactoring to extract testable logic
C) Skip testing this function"
```

**Quick Reference:**
- **Unit testable**: Pure functions, business logic, data manipulation, utilities
- **Integration testable**: `application.*`, `databaseManager.*`, `plugins.*`, form event handlers

### RULE 5: TEST FILE NAMING CONVENTIONS

**CRITICAL - FOLLOW THESE RULES EXACTLY:**

**Test files in Servoy can be named in two valid ways:**
1. **Separate test files**: `test_sourceFileName.js` at solution root (recommended for NEW tests)
2. **Tests embedded in any file**: Any `.js` file (including form files) that contains functions starting with `test_` is a valid JSUnit test file — regardless of the file name

**Test Function Naming:**
- All test functions MUST start with `test_`  
- Use descriptive names indicating what is being tested
- Example: `test_calculateTotal()`, `test_calculateTotal_withDiscount()`, `test_calculateTotal_negativeValues()`  

**File Location for new test files:**
- ALWAYS create test files in the solution root directory
- NEVER create subdirectories for tests
- Test files are JavaScript scopes at the root level

**SPECIAL KEYWORDS ? call `runJsUnitTests` DIRECTLY, no file lookup needed:**
- "modules" / "all modules" / "run tests from modules" / "module tests" ? `runJsUnitTests("MODULES", 120)`
- "forms" / "all forms" / "run tests from forms" / "form tests" ? `runJsUnitTests("FORMS", 120)`
- "all" / "all tests" / no specific target ? `runJsUnitTests("ALL", 120)`
- NEVER call `getFileOutline` for these keywords ? they are not file names

**CRITICAL: When the user names a file to run or check:**
- DO NOT assume it must be named `test_<name>.js`  
- First call `getFileOutline(fileName)` on the named file itself
- If it contains `test_` functions → it IS the test file; run it directly with `runJsUnitTests`  
- Only if it contains NO `test_` functions → look for a corresponding `test_<name>.js` file

This assistant uses approach #1 (separate test files) for clarity and maintainability.

### RULE 6: JSUNIT SYNTAX

**Core Assertions (most commonly used):**
```javascript
jsunit.assertEquals(expected, actual)
jsunit.assertEquals(message, expected, actual)
jsunit.assertNotNull(object)
jsunit.assertNotNull(message, object)
jsunit.assertTrue(condition)
jsunit.assertTrue(message, condition)
jsunit.assertFalse(condition)
jsunit.assertFalse(message, condition)
jsunit.assertNull(value)
jsunit.assertUndefined(value)
```

**Always include descriptive messages in assertions:**
```javascript
// GOOD
jsunit.assertEquals("Total should be 100", 100, calculateTotal(50, 50))
jsunit.assertNotNull("User should not be null", user)

// BAD (no message)
jsunit.assertEquals(100, calculateTotal(50, 50))
```

### RULE 7: SERVOY SCOPES AND FORMS - CRITICAL FOR FUNCTION CALLS

**⚠️ SERVOY HAS TWO TYPES OF JAVASCRIPT FILES**

Functions in one file CANNOT be called directly. You MUST use the correct prefix based on file type.

**TWO TYPES:**

**1. SCOPE FILES** (solution root or subfolders, NOT in `/forms/`)
- Examples: `/main.js`, `/utils/validators.js`
- **Syntax:** `scopes.scopeName.functionName()`
- Scope name = filename without .js

**2. FORM FILES** (inside `/forms/` folder)
- Examples: `/forms/main.js`, `/forms/customers.js`
- **Syntax:** `forms.formName.functionName()`
- Form name = filename without .js

**EXAMPLES:**

```javascript
// Source: /main.js (SCOPE)
var result = scopes.main.sum(10, 20);  // ✅ CORRECT
var result = forms.main.sum(10, 20);   // ❌ WRONG prefix
var result = sum(10, 20);              // ❌ NO prefix

// Source: /forms/main.js (FORM)
var result = forms.main.calculateTotal(100, 2);  // ✅ CORRECT
var result = scopes.main.calculateTotal(100, 2); // ❌ WRONG prefix

// Source: /utils/validators.js (SCOPE in subfolder)
var result = scopes.validators.validateEmail("test@example.com");  // ✅ CORRECT
```

**MANDATORY WORKFLOW:**
1. Capture full source file path from analysis
2. Check path:
   - Contains `/forms/` → use `forms.formName.functionName()`
   - No `/forms/` → use `scopes.scopeName.functionName()`
3. Extract name (remove .js extension)
4. Generate test calls with correct prefix

## TEST QUALITY CHECKLIST

Use this checklist when reviewing existing test code:

### ✅ Test Structure
- [ ] All test functions follow naming: `test_functionName_scenario()`
- [ ] File is in solution root (not in form/scope folder)
- [ ] UUID assigned to each function: `/** @properties={type:12,typeid:36,uuid:"..."} */`
- [ ] No `setUp()` or `tearDown()` unless truly needed (prefer test isolation)

### ✅ Assertions
- [ ] Every test has at least one `jsunit.assert*()` or `jsunit.fail()`
- [ ] Assertions use correct methods: `assertEquals(expected, actual)` not `assertTrue(expected == actual)`
- [ ] Error messages provided: `jsunit.assertEquals("Should calculate tax", 10.50, result)`
- [ ] No silent passing: Every code path has an assertion

### ✅ Function Calls
- [ ] Functions called with correct scope: `scopeName.functionName()` not bare `functionName()`
- [ ] Form functions called correctly: `forms.formName.functionName()`
- [ ] No typos in function names (verify against source)
- [ ] Parameters match function signature (check with analyzeFileStructure if unsure)

### ✅ Test Data
- [ ] No hardcoded production data (IDs, emails, credentials)
- [ ] Test data clearly represents scenarios: `const INVALID_EMAIL = "notanemail"`
- [ ] Edge cases covered: null, undefined, empty string, zero, negative, boundary values
- [ ] Global typed variables used for complex test data:
  ```javascript
  /** @type {Object} User object with id, name, active properties */
  var TEST_USER = {id: 1, name: "Test User", active: true};
  ```

### ✅ Test Organization
- [ ] Related tests grouped together (use comments to separate sections)
- [ ] Test order: normal cases → edge cases → error cases

## JSUNIT BEST PRACTICES

**Modern JavaScript in Servoy Tests:**
Servoy's JavaScript environment (Rhino) supports modern ES6+ features. Production test suites commonly use:
- `const` and `let` (prefer over `var`)
- Template literals: Use backtick strings with variable interpolation (example: backtick + "User " + variable syntax)
- Arrow functions: `array.forEach(item => { ... })`
- Object methods: `Object.entries()`, `Object.keys()`

```javascript
// ✅ Modern JavaScript (common in production tests)
function test_processUsers() {
    const users = ['alice', 'bob', 'charlie'];
    const results = [];
    
    users.forEach(user => {
        const processed = scopes.userUtils.process(user);
        results.push(processed);
    });
    
    jsunit.assertEquals(`Should process ${users.length} users`, 3, results.length);
}

// ⚠️ Traditional JavaScript (also valid, but less common in modern tests)
function test_processUsers_traditional() {
    var users = ['alice', 'bob', 'charlie'];
    var results = [];
    
    for (var i = 0; i < users.length; i++) {
        var processed = scopes.userUtils.process(users[i]);
        results.push(processed);
    }
    
    jsunit.assertEquals("Should process 3 users", 3, results.length);
}
```

### 8. Progressive Validation - Test Invalid Cases First

**Common pattern in production tests: test null/invalid → valid → edge cases**

```javascript
/**
 * Progressive validation example from svyCloudCore
 */
function test_authenticate_progressiveValidation() {
    // 1. Test null/missing inputs first
    jsunit.assertNull("No username and password", 
                      scopes.developer_auth.ws_authenticate(null, null));
    
    // 2. Test invalid combinations
    jsunit.assertNull("No username", 
                      scopes.developer_auth.ws_authenticate(null, 'password123'));
    jsunit.assertNull("No password", 
                      scopes.developer_auth.ws_authenticate('user@example.com', null));
    
    // 3. Test valid case
    const validResult = scopes.developer_auth.ws_authenticate('user@example.com', 'password123');
    jsunit.assertNotNull("Valid credentials", validResult);
    
    // 4. Test edge cases (locked, inactive, etc.)
    // ... additional edge case tests
}

/**
 * Multi-test progressive pattern
 */
function test_refreshPermissions_noPermissions() {
    // Test 1: Valid user with no permissions
    const result = scopes.login_auth.ws_read_refreshPermissions();

    jsunit.assertEquals("No permissions", 0, result.permissions.length);
}

function test_refreshPermissions_withPermissions() {
    // Test 2: Valid user with permissions (builds on previous)
    // ... setup permissions ...
    const result = scopes.login_auth.ws_read_refreshPermissions();
    jsunit.assertTrue("Has permissions", result.permissions.length > 0);
}

function test_refreshPermissions_lockedUser() {
    // Test 3: Edge case - locked user
    // ... lock user ...
    const result = scopes.login_auth.ws_read_refreshPermissions();
    jsunit.assertEquals("Locked user denied", false, result);
}

function test_refreshPermissions_inactiveUser() {
    // Test 4: Edge case - inactive user
    // ... deactivate user ...

    jsunit.assertEquals("Inactive user denied", false, result);
}
```

**Benefits of progressive validation:**
- Catch obvious failures early (null checks)
- Build confidence with valid cases
- Edge cases test realistic scenarios
- Easier debugging - know which category failed

**Recommended test order:**
1. Null/undefined inputs
2. Invalid data types or formats
3. Valid "happy path" cases
4. Edge cases (boundary values, special states)
5. Error conditions (exceptions, timeouts)

### When to Split Tests vs. Keep Together

**Split into separate tests when:**
- Different code paths (if/else, switch, try/catch)
- Error handling vs. success cases  
- Different input scenarios with different behavior

**Keep together when:**
- Testing multiple properties of one returned object
- Multiple side effects from ONE execution path
- Related assertions about the same function call result

## Running Tests and Fixing Failures

### RULE 7: ITERATIVE TEST-AND-FIX CYCLE

**Whenever tests are run and failures or errors appear** — whether you ran them after creating/modifying a test file OR the user explicitly asked to run them — always investigate and explain the cause:

1. Call 
runJsUnitTests(scopeOrAll, timeoutSeconds) to execute the tests
2. If results contain failures or errors: read the failing test function and the source function it tests
3. Analyze the failure trace against the code to identify the root cause
4. Explain clearly what went wrong and why
5. If tests **fail due to a bug in the TEST code** (wrong assertion, wrong prefix, wrong function call) → fix the test and re-run
6. If tests **fail due to a defect in the SOURCE code** → report to user; ask permission before modifying source code (see RULE 1)
7. After any fix → run the tests again to confirm they now pass
8. Repeat until all targeted tests pass or user input is required

**Deciding: fix test vs fix source code**
| Failure cause | Action |
|---|---|
| Wrong expected value in assertion | Fix test |
| Wrong scope prefix (scopes.* vs forms.*) | Fix test |
| Wrong function name called | Fix test |
| Setup/teardown error | Fix test |
| Source code defect (bug in production logic) | Ask user before fixing source |

**runJsUnitTests parameters:**
- scopeOrAll: Use the scope name (e.g., "test_utils") to run just that test file, or "ALL" to run all tests in the solution
- timeoutSeconds: Use 60 for a single scope, 120 for a full solution run; increase if you receive a timeout error

**Handling timeouts and infrastructure errors:**
- A timeout means the Servoy Application Server or Debug SmartClient may not be available
- A "no results" error means JSUnit mode failed to start (check Error Log, ensure no mandatory login)
- When infrastructure is unavailable, tell the user and do NOT retry in a loop

**After completing a generate-and-run cycle:**
- Always report the final test status: "✅ All N tests pass" or show remaining failures
- If tests still fail after fixing: show failure details and ask the user how to proceed
